# 题目交互可视化：阶段工作汇报与后续计划
10.20
## 一、工作目标与阶段成果
目标是将一道题的图片转换为可直接打开的交互式 HTML 教学页面，让刚读完题、尚不知道解法的学生，通过图形、分步变化和有意义的操作，理解条件如何转化、关系如何建立，以及答案怎样得到。
目前已完成从单次生成到“生成—检查—审核—修改—留档”的本地实验工作台，并围绕输入方式、模型选择、解题规划、提示词、页面实现结构和修订方式做了多组探索。在此基础上，开始建立覆盖数学、物理、化学的小型 Benchmark，将后续优化从少数例题上的反复调试转向固定题集上的可复现比较。
| 工作方向 | 已完成内容 | 当前边界 |
| --- | --- | --- |
| 可视化工作台 | 图片上传、配置和模型选择、同题多方案对比、阶段日志、逐轮 HTML 预览、模型评分、人工评分、历史保存 | 能运行和追溯，不等于生成页面已经达到稳定教学质量 |
| Prompt 体系 | 拆成通用可视化要求、学科经验、输入输出约束；审核提示词独立管理 | 多学科提示词已具备，充分的跨学科效果验证尚未完成 |
| Workflow 探索 | 图片直传、OCR＋文本、规划后生成、规则增强、推理强度、分步 SVG 示例、固定模板、局部修订 | 前期主要围绕少量数学题探索，部分实验存在 Prompt 或审核版本差异 |
| DeepSeek 改进 | 原图输入、开启推理、显式条件转化、统一状态联动、分步 SVG、局部修订 | 得到较好的具体案例，尚不能认定普遍达到 GPT 水平 |
| Benchmark 建设 | 36 道候选题及本地题图、答案、解析、元数据；开发集和留出集各 18 道 | 仍为候选版本，题族与答案尚需复核 |
| 评价工具 | 五维评分、综合评分、匿名人工评分界面、独立模型评测和结果留档 | 最新方向是先统一使用 GPT 独立评分，暂缓评委模型的人类一致性比较 |
## 二、系统架构与工程建设
### 2.1 当前主流程
```text
题目图片
  ↓
选择学科／可选自动识别数学、物理、化学或其他
  ↓
拼装 Prompt 并冻结任务配置
  ↓
DeepSeek 生成完整 HTML
  ↓
本地结构与离线资源检查 → Chrome 渲染 → 截图与部分交互检查
  ↓
DeepSeek 流程内审核：原题图＋HTML 源码＋页面截图
  ├─ 需要修改且未达轮次上限 → 带原图、上一版 HTML 和意见继续修订
  └─ 结束 → 保存各轮结果，并选内部综合分最高的一轮，同分取较后轮
  ↓
GPT 独立评价：原题＋参考答案与解析＋完整源码＋页面与操作证据
  ↓
按题目、学科和 workflow 汇总质量、稳定性、token 与耗时
```
流程内 reviewer 用于推动修改；独立 judge 用于衡量最终效果。当前将两者分开：生成与返修链路主要使用 DeepSeek，GPT 的评分不反馈给本次生成流程，也不参与选择内部最佳轮次，避免把评价过程变成另一轮生成优化。
每次迭代是新的 API 请求，带上必要的固定提示词、题图、上一轮页面和审核意见，而非无限累积全部聊天记录。支持已保存任务恢复，审核失败时尽量复用待审核 HTML，避免重复生成。
### 2.2 工作台与可追溯记录
已提供以下功能：
- 上传题图并按时间戳保存；每轮 HTML、截图、审核和元数据均带时间戳及轮次。
- 在同一界面选择不同生成模型、审核模型、输入路径和 Prompt 配置，进行同题对比。
- 显示运行日志、当前阶段、逐环节和逐轮耗时、任务累计 token，以及已知价格部分的费用估算。
- 历史页面展示当时的模型和配置，保存 Prompt 快照，避免后续修改提示词后无法复现旧结果。
- 保存模型评分与人工评分，五个维度与综合分分别记录，评分绑定具体 HTML 哈希，保留修改历史。
- 数据保存在本地，原工作台历史位于 data_v2；Benchmark 运行与评测产物单独保存，避免混入旧实验。
常规迭代模式可以达到最多五轮，也支持通过即停止或固定轮数实验。新 Benchmark 首批采用一轮和固定三轮，不能将不同轮数的任务当作相同预算比较。
### 2.3 Prompt 的结构与学科经验
生成提示词采用三部分：
| 部分 | 核心内容 |
| --- | --- |
| 通用可视化要求 | 面向刚读题的学生；先展示已知与所求；显式呈现条件转化；以图形和交互为主，文字只作必要说明；公式中的量要能对应到图上 |
| 学科经验 | 数学强调几何约束、合法参数、定义域和端点；物理强调研究对象、正方向、量纲、受力和过程；化学强调宏观现象、粒子、符号方程及守恒关系 |
| 输入输出与渲染要求 | 直接在响应正文输出完整 HTML；单文件、自包含、离线运行；限制大小；不依赖工作区写文件能力；避免未渲染公式、外链资源和缺字字符 |
审核提示词也独立维护，重点检查题意、学科正确性、图文联动、教学顺序及实际页面效果。例如，一个滑块影响多个区域时，反馈区域应便于同时观察；复杂图形应控制信息密度，检查字母、箭头和数值的重叠。
已将相关 skill 的可用方法整理进提示词：数学借鉴 interactive-whiteboard、math-teacher、math-skills，以及本地 interactive-math-html、math-visualization-workflow；物理借鉴 create-visualization、advanced-visualization、matterjs 的过程、约束与重置思路；化学借鉴 chem-vis 等的粒子和结构表达方法。这里主要是将适用经验转化为模型可执行的生成要求，并非在每次 API 请求中运行这些 skill 或安装全部依赖。
## 三、前期探索了哪些模型与 Workflow
### 3.1 模型使用情况
下表列的是已有实验记录中的模型标识，不将“接口目录中能看到的模型”全部视为经过完整验证。
| 模型或环境 | 主要用途与阶段 |
| --- | --- |
| Codex 交互环境、Codex＋Sites skill | 简短提示直接制作页面的 baseline，以及人工查看的设计参考；没有完整统一条件的 baseline 排名 |
| gpt-6-sol | 早期图片直传 HTML 生成，形成后续分析教学结构与页面实现方式的参考案例 |
| gpt-5.6-sol | 早期 GPT 流程的审核；也有早期单轮生成对照记录；当前选择为独立 GPT judge |
| qwen3.6-35b-a3b | 图片直传和 OCR＋文本生成对照 |
| qwen3.6-flash | 图片直传、文本生成、题目 OCR、截图描述、规划或页面审核等探索 |
| deepseek-v4-flash-0731 | 早期图片直传、OCR＋文本，以及规划路线实验 |
| deepseek-v4-1-flash-260910 | 更新型号后的直接生成与规划生成跟进 |
| deepseek-v4-1-flash-261017 | 当前重点：原图生成、规划、流程内审核、整页返修和局部修订 |
调用使用项目现有网关和接入方式。不同型号、密钥路由、Prompt 版本或审核模型同时改变的历史实验，仅作探索证据，不能直接解释为模型能力的单变量差异。当前生产候选 workflow 不再采用 OCR 作为默认输入路径。
### 3.2 单次生成与生成—审核闭环
最简单的 baseline 是“题目图片＋希望直观看懂答案由来的简短要求→HTML”，用于观察模型不加额外流程时的表现。另有 Codex 借助 Sites skill 制作的页面参考，视觉和交互完成度较好，但实际检查仍发现证明中的计算问题。
随后实现“生成→本地检查→模型审核→返修”的闭环。早期 GPT 案例采用 gpt-6-sol 生成、gpt-5.6-sol 审核；能够形成较完整的椭圆、斜率、极值等交互演示，但仍存在控制参数出现过早、推导跳步等问题。
关键认识是：增加轮次不保证单调提升。某轮已经较好，整页重写后仍可能出现脚本错误或新的标注重叠，因此需要保存全部轮次并保留最佳版本。
### 3.3 图片直传与 OCR＋文本对照
两条路径分别为：
```text
图片直传：
原图 → 多模态生成 → 页面渲染 → 原图＋页面图＋源码审核 → 修改
OCR＋文本：
原图 → 一次题目 OCR 与图形关系描述 → 文本生成 → 页面渲染
     → 每轮截图描述 → 原题转写＋截图描述＋源码审核 → 修改
```
OCR 结果在同一任务后续轮次复用，同题且识图配置一致时也可复用，避免反复识别原题。它可以让文本模型参与，但增加了公式、希腊字母、几何关系转写错误，以及页面描述丢失细节的风险。
曾在同一道椭圆题上，用 Qwen 35B、Qwen Flash、DeepSeek V4 Flash 分别运行两种路径，共六组固定五轮实验。同一路径内共用原版生成 Prompt 和 Qwen Flash 审核，OCR 组三种模型复用同一份转写；此前额外加入“精简交互”要求的试跑保留为探索记录，不并入这批受控比较。
| 生成模型 | 图片直传观察 | OCR＋文本观察 |
| --- | --- | --- |
| Qwen 3.6 35B | 有较完整的图形，但出现极值答案错误；某轮被自动审核误评为 5 分；部分轮次脚本错误 | 部分轮次文字答案正确，动态计算却漏掉平方项，使点偏离曲线 |
| Qwen 3.6 Flash | 有轮次给出正确核心答案，也有脚本错误和审核误判 | 有轮次答案正确，但数值表格仍有显示错误；出现长输出截断 |
| DeepSeek V4 Flash | 页面可以运行，但多轮误读点线关系或未正确完成原题 | 比直接图片更接近几何结构，但仍反复算错最值，审核也有漏判 |
这批结果说明 OCR 有时能帮助表达题意，但不能保证数学或动态图正确，也不是更短、更便宜的固定选择。由于两条路径的生成输入和审核材料都不同，路径间比较的是完整 workflow，而非单独测量 OCR 的一个因素。
### 3.4 先规划、核对，再生成页面
为减少“直接写 HTML 时同时解题、设计、编码”的负担，增加了公开、可检查的结构化规划：
```text
题目 → 已知与目标 → 逐步推导与答案 → 教学分镜与交互设计
     → 规划核对与必要修改 → HTML 生成 → 页面审核与修订
```
规划明确记录独立变量、衍生量、合法范围，以及每一步展示什么、学生做什么、应当理解什么。最初在 OCR＋文本路径实验，后续代码已支持原图直接输入规划模型，并在页面中展示保存的规划内容。
三角形、抛物线、双曲线与椭圆组合题上，探索过 Qwen Flash、DeepSeek V4 Flash、DeepSeek 260910 和 DeepSeek 261017 的直接生成与规划生成。观察到：
- 简单题的教学顺序与控件组织有改善，部分页面更稳定。
- 规划增加调用、token 和耗时；规划核对不通过时，可能在生成 HTML 前结束任务。
- 复杂题依然会出现错误规划被核对模型接受，页面继续沿用错误答案，最终审核还给出高分的情况。
因此，规划是可比较的候选 workflow，不是已经证明有效的通用正确性保障。新 Benchmark 中暂未将规划方案纳入首批，数学以外的规划协议还需单独冻结。
### 3.5 DeepSeek 原图直传的专项改进
10 月 19 日围绕 deepseek-v4-1-flash-261017，采用原图输入，重点比较以下方案：
| 方案 | 改动 | 主要观察 |
| --- | --- | --- |
| 原完整 Prompt | 保留旧提示词，不开启推理 | 仍会误读几何条件或省略结论 |
| 规则增强 | 加强坐标、参数范围、边界和图文一致性检查 | 规则变多并未自动消除数学和脚本错误 |
| 开启推理 | 在规则一致的基础上调整推理开关 | 有助于部分复杂条件转化，但推理输出和延时明显增加 |
| 分步 SVG＋教学示例 | 加入与目标题不同的教学示例，强调单一状态驱动图、公式和数值 | 得到较好的教学过程展示，是当前继续使用的主要方向 |
| 低推理强度 | 保持提示词，减少推理量 | 测试成本与质量取舍；样本不足以断言不会损失质量 |
| 固定 HTML/SVG 框架 | 固定布局与控件，模型生成题目相关教学模块 | 减少重复代码，但暴露步骤索引、图表缩放及表达受限等问题，未稳定胜出 |
| 局部修订 | 对已有 HTML 返回 old/new 精确替换，修复后仍保存完整页面 | 能减少无关重写与回退风险；补丁必须唯一匹配，失败则拒绝应用并留档 |
从 GPT 成品中总结和迁移的是可观察的方法：题设先入场、条件转化分步展示、图形与公式同色对应、主图与局部图联动、统一参数和坐标、就近反馈。没有获取或复用 GPT 的私有思维链，也没有把目标题的 GPT 答案直接塞给 DeepSeek。
专项实验记录了 12 个生成／修订任务、29 轮 HTML，另有历史 GPT 页的同标准重审。椭圆较好案例经历了前序五轮整页生成和三轮局部修订；抛物线案例经历三轮整页生成和一轮局部修订，不能将最后的一轮修补当作从零生成成本。
椭圆局部修订页与历史 GPT 页的同标准审核均得到综合 4 分；对点坐标、曲线约束、斜率、取等位置等又做了浏览器操作与独立数值检查。这支持“在少量具体例题上获得接近历史 GPT 参考的结果”，不支持“DeepSeek 已对任意题稳定等同 GPT”。
这轮专项搜索记录的总用量约 235.6 万 token、累计 API 时间约 164.9 分钟，包含多方案试错、失败和重试，不是单个页面的正常生成预算，也不是并行实验的墙钟时间。局部修订观察到输出与时间缩短，但当时推理设置也有变化，尚不能给出普适降本比例。
## 四、主要问题与已有修正
| 问题 | 实际表现 | 已采取的处理 |
| --- | --- | --- |
| 题设被误读或交互破坏约束 | 错把题设点当原点；默认参数无解；滑块改变固定条件 | 先求完整可行域，再设置控件；普通状态、临界状态、复位和动画路径共同核对 |
| 答案正确但教学不清楚 | 上来就调斜率，不解释斜率如何由角度、中点等条件转化而来 | 要求“题设→表示→关系→目标量→结论”，先说明控制量来历，再开放操作 |
| 图、公式、代码不一致 | 正文结论正确，动态点偏离曲线或数值沿用旧状态 | 统一状态和派生计算，增加实际操作与数值检查 |
| 页面信息过密 | 字母、当前值与最优值重叠；控件与反馈相隔太远 | 分步显示对象、增加局部图、就近反馈、检查边界和取等状态 |
| 曲线与符号显示问题 | 抛物线有明显折角；组合向量字符缺字；LaTeX 原样显示 | 优先原生 SVG 曲线或足够精度的路径，使用 SVG 箭头及可靠的上下标排版 |
| 长输出与超时 | HTML、审核 JSON 或截图描述达到上限；部分预算全被推理消耗 | 分清失败环节，按任务提高上限或超时、记录推理设置变化、复用已有产物 |
| 网关与解析问题 | 429、503、连接失败、DNS 波动；数学反斜杠与引号导致 JSON 解析异常 | 保存错误与原始响应、重试和续跑；将网络问题、截断问题与内容问题分别记录 |
| 审核误判 | 错答案获 5 分，或正确答案被要求改错 | 引入独立参考解、实际操作证据与外部 judge；不把 reviewer 分数当真值 |
工程验证覆盖了配置和 Prompt 拼装、图片与 OCR 输入、规划、局部补丁、任务恢复、评分元数据和接口。评分页也做过浏览器操作验证，包括 0 分保存、提交后切换、重新打开恢复记录；测试记录与真实人工评分隔离。上述验证只证明相应软件行为，并不证明所有页面的学科内容正确。
当前浏览器检查以桌面真实呈现为准，并尝试部分可见按钮或滑块；不再将未经实测的手机宽度作为扣分依据。自动操作未遍历所有拖拽、动画、参数边界，专项数学验算也仅适用于已编写检查器的具体题目。
## 五、小型 Benchmark：怎么选、怎么构造
### 5.1 建设动机
前期持续围绕少数解析几何题调 Prompt，容易出现“这个例子变好了，但不知道其他题是否也更好”的情况。因此需要固定题集、固定输入和评价口径，保留未参与调参的题目，衡量不同 workflow 的泛化效果和真实成本。
### 5.2 题源与选题口径
使用现有题库的 1,875 道去重题目及其 Schema。全部题目都有非空题干、答案、解析；其中高中数学 1,719 道、物理 69 道、化学 87 道。
当前选出 36 道候选题，三个学科各 12 道。没有按原题库比例随机抽样，否则数学会占据绝大部分测试集。采用明确主题名额，参考本地知识点频率、题型、难度标签和可视化方式，挑选能够覆盖不同表达需求的题目。
这里的“频率”是该批本地题库中的知识点出现频率，不代表全国考试频率。例如数学中集合交集、不等式和函数最值较常见；物理偏运动学；化学偏实验与制备。频率用于辅助选择，不替代跨主题覆盖，也尚未实现完整的题型／难度分层统计配额。

| 数学 | 12 | 二次函数与最值、集合与不等式、向量数量积、三角函数图像、立体几何、椭圆、条件概率、统计分布、等比数列、等差数列、不等式最值、导数与切线 |

### 5.3 开发集与留出集
每科暂分 6 道开发题和 6 道留出题，共 18＋18。当前脚本按固定选题清单的奇偶编号分配，保证可复现；这不是经过优化的随机分层划分，也不保证开发与测试都有相同主题。
开发集用于调试 workflow、Prompt 和评分规则；留出集在方案与评价标准冻结后再运行。首批只使用三个开发题，每科一道，不启动全部 36 道的付费生成。
去重方面，题库先按题目 ID 去重，候选集再做文本相似度辅助检查。目前未触发相似度阈值，但这种检查不能证明没有语义相近的题族。正式冻结前仍要复核近似题、旧调参题的变式，以及跨集合泄漏。
### 5.4 从题库到固定模型输入
```text
题库原始记录
  ↓
按固定清单选题，保存来源 ID、知识点、难度、试卷来源和入选理由
  ↓
清理题干 HTML 中的活动内容，下载并本地化公式 SVG 与图形资源
  ↓
将完整题干渲染为固定 input.png，计算内容哈希
  ↓
分别保存参考答案、解析与核查状态
  ↓
生成端只接收题图；独立 judge 可以接收参考资料
```
题图准备环节不调用模型，也不使用 OCR。模型接收的是由题库题干及原有公式／图形资源渲染出的固定图片，便于不同 workflow 使用完全一致的输入。答案与解析独立存放，不进入候选生成提示词。
每题保存原始记录、题干 HTML、题图、资源清单、参考答案与解析、检查记录；总索引保存题集版本、来源和输入哈希。运行时另存真实 Prompt、模型标识、配置、逐轮产物、API 用量和耗时。
```text
benchmark/
├─ math/、physics/、chemistry/     每科 12 道题
├─ manifest.json、coverage.json  选题、版本、覆盖与限制
├─ workflows/                   方案登记、配置与 Prompt 快照
├─ runs/                        每个任务的逐轮 HTML、截图、审核与调用记录
├─ evaluation/                  独立 GPT 评价及保留的人工标注工具
├─ 人工评分/                     已归档的历史人工评分页面、来源与参考解
└─ reports/                     实验汇总与评价报告
```
### 5.5 当前版本的限制
当前版本为 v1-candidate，36 道题的资源和题图均已准备好，但还不是全面审定的标准答案测试集。
- 物理题池偏运动学，波动主题缺失，光学与热学样本较少。
- 化学有机合成、元素周期律等覆盖不足，部分题同时涉及多个主题。
- 数学、物理、化学的题量被平衡，但难度和题型分布仍需复核。
- 题库提供答案不等于答案已独立验证；参考解有疑问时应先核查，不直接用来判模型错误。
- 历史人工评分页面单独归档，不并入新留出集；旧调参样例也不能用来证明新方案的泛化能力。
## 六、当前受控实验与评价方案
### 6.1 首批三种 Workflow
首批使用二次函数值域、匀减速运动、溶液电导与离子反应三个开发题，每题运行以下三组，目标共 9 个最终候选页面：
| 编号 | 流程 | 轮数 | 当前控制条件 |
| --- | --- | ---: | --- |
| W0 | 原图单次生成，执行检查和内部审核，但不返修 | 1 | DeepSeek 261017；同题图、同学科基础 Prompt |
| W1 | 原图生成＋内部审核＋整页返修 | 固定 3 轮 | 生成和审核均使用 DeepSeek 261017 |
| W2 | 首轮完整 HTML＋审核＋局部补丁修订 | 固定 3 轮 | 与 W1 保持相同推理强度，主要改变修订方式 |
首批生成和流程内审核均使用 deepseek-v4-1-flash-261017，开启推理，使用 high，输出上限 64,000 token、超时 900 秒；上限不等于实际消耗。W1 与 W2 的修订推理强度统一为 high，避免重复早期“修订方式与推理强度同时变化”的比较问题。
同一科内使用相同基础生成与审核 Prompt；数学使用已整理的分步 SVG 经验，物理与化学使用各自学科经验。跨学科汇总时应分别报告，不把学科差异当作 workflow 差异。
当前按内部综合分选出每个任务的一轮作为独立评测候选，同分取较后轮；所有轮次继续保留。后续还可比较首轮、最后一轮和选中轮的质量，判断迭代是否存在回退。
### 6.2 最新决定：GPT 独立评分
当前统一使用 gpt-5.6-sol 作为独立 judge，暂缓“先人工标注，再选择最接近人工的评委模型”的校准实验。已有人工评分和工具仍保留，但不阻塞新的 GPT 评价。
judge 至少接收完整 HTML 源码，包括 CSS 和 JavaScript，同时接收：
- 原题图片；
- 参考答案与解析，以及其来源和核查状态；
- 页面初始截图与实际操作后的截图；
- 操作记录、脚本异常等检查证据。
源码用于检查计算、约束和交互逻辑，截图用于检查布局、图形和标注效果。judge 不接收人工分数、原 reviewer 分数或生成模型身份作为评分依据，也不能将没有实际操作证据的功能宣称为已经验证。
| 评分维度 | 核心问题 |
| --- | --- |
| 一致性 | 是否保留题设对象、条件、各小问与允许范围 |
| 正确性 | 推导、计算、图中数值、定义域、边界和最终答案是否正确 |
| 页面效果 | 图形与公式是否清楚，是否有重叠、裁切、信息过密 |
| 交互效果 | 交互是否有教学意义，控制量与取值是否合理，反馈是否同步且便于观察 |
| 教学效果 | 学生能否从刚读完题开始，理解关键转化与答案产生，而不是被直接告知结论 |
五维各 1–5 分，综合评分另给 0–5 分，不简单取均值；未核实项允许留空。GPT 的分数仍是模型评价，不等于经过人类校准的真值。
### 6.3 历史人工评分的归档与参考解
本次已核验并归档了 3 个带完整人工评分的页面，涉及 2 道题。这是本次实际导入的范围，不代表仓库中只有三道题，也不是对所有历史标注的完整统计。
归档保留 HTML、题图、截图、原始人工评分、来源元数据和 HTML 哈希。原 data_v2 文件保留，以免影响旧工作台历史链接。
这两道题未在给定题库中找到精确题源，按要求独立补写了参考答案和解析：
- 抛物线、重心与面积比：曲线 x²=8y 且 y>0；面积比范围为 (1/6,13/60)。
- 椭圆对称弦：m²>2/3；三角形面积最大值 √2/2，在 m=±√2 时取得。
参考解包含推导、可行域、退化情形和数值交叉核验，标明为本次独立推导、待人工复核，而非题库原答案，也不是从待评价 HTML 提取的自述。

## 七、后续计划与验收方式
| 阶段 | 下一步工作 | 预期产出与验收 |
| --- | --- | --- |
| 1. 完成首批验证 | 跑完三科各一道、W0/W1/W2 共 9 个候选，完成统一 GPT 评分；保留失败和重试 | 页面、所有轮次、独立评分、token、耗时齐全，形成同题对照表 |
| 2. 冻结题集 | 复核题图、答案、近似题族、难度和题型；补充物理波动等缺口，必要时调整划分 | 固定题集版本、输入哈希、参考解版本和开发／测试清单 |
| 3. 扩展开发集实验 | 将表现值得继续的 workflow 扩展至其余开发题；需要时加入规划方案 | 判断改进是否跨题、跨学科有效，而非仅优化某一道题 |
| 4. 分析质量与成本 | 按学科、知识点和 workflow 汇总五维分、综合分、严重错误、运行失败、轮次、token 和耗时 | 识别质量收益来自哪里、付出了多少额外调用；保留长尾失败案例 |
| 5. 一次性留出评测 | 冻结 Prompt、模型、轮次、推理强度和 judge 之后再运行留出集 | 得到未参与调参题目上的结果；不根据留出集表现继续定向改同一版本 |
| 6. 必要的人工抽查 | 抽查高分但存在疑点、严重错误、方案差异大的页面；后续有需要再恢复 judge 校准 | 防止自动高分掩盖学科错误；人工评分继续独立保存 |
控制变量方面，同一道题应固定图片、学科 Prompt、模型版本和审核口径，只改变本次要比较的 workflow 组件。改变 token 上限、超时、推理强度、框架或参考解时必须留下配置版本，不将不同条件的自动分数混成一个胜率。
统计方面，以题目为主要比较单位，同题多个版本不能当作多个独立题目。先做逐题配对比较，再按学科汇总；在少量题上观察到优势后，应通过更多题和必要的重复运行检查稳定性。
成本方面，分别统计生成、规划、审核、返修、截图描述和独立 judge 的消耗；保留有返回用量的失败调用。API 累计时间、端到端墙钟时间分别报告。当前人民币估算只覆盖已知的缓存读取 ¥1.44／百万 token、写入 ¥5.76／百万 token，普通输入和输出单价未确认，不能据此报完整总费用。
## 八、阶段结论
目前已经具备一个可以持续做实验的可视化工作台：能生成、检查、迭代、记录、比较，并开始用固定的数理化题集开展评测。
前期最有价值的发现是：页面质量主要受题意理解、数学与代码一致性、教学条件转化、交互状态管理和返修稳定性共同影响；增加提示词、规划环节、框架或轮次都不必然提升效果。DeepSeek 已出现较好的案例，但仍需要独立评测和更广覆盖的题集验证。
下一阶段的重点是完成“固定 Benchmark＋受控 DeepSeek workflow＋独立 GPT 评分”的闭环，形成可复现的质量、稳定性和成本结论，再据此决定保留哪种流程。
